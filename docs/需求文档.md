# App Review Insights —— 产品需求文档（PRD）

> 版本：v1.0　|　日期：2026-08-13　|　状态：草稿（供评审）
> 配套文档：`docs/设计方案.md`（技术基线，含决策记录 D1–D9）
> 依据：retro-labs/app-review-insights 项目资料整理

## 1. 项目概述

### 1.1 背景

App Store 用户评论蕴含真实产品反馈，但原始评论规模大、噪声多、语言混杂、观点分散，难以直接转化为可执行的产品计划。本项目构建一个**可运行的 Web 应用**：输入一条美国区 App Store 应用链接（可附加分析目标/约束），系统自动完成"采集 → 清洗 → 动态分析 → 证据评估 → PRD → 测试用例 → 可追溯性验证"的完整工作流，并在 UI 中可视化进度、中间结果与最终交付物。

### 1.2 目标

- **核心目标**：从真实用户评论中识别问题，并将其转化为可执行的产品需求与测试计划。
- 系统**不得依赖任何应用特定的硬编码**（类别、发现、需求、测试用例均须动态生成）。
- 至少一个核心语义任务（动态主题发现 / 问题整合 / 基于证据的分析 / 需求生成 / 测试用例生成）必须由**模型驱动**，仅靠关键词、正则、查找表不满足要求。
- 内置**多个常见 LLM 提供商**供用户选择，用户填写 API Key 后使用；支持本地模型（无需 Key）。
- 支持导入 JSON / CSV 评论数据集，支持处理**未见过的应用链接**与**新的分析目标**。

### 1.3 非目标（Out of Scope）

- 不做 App Store 之外渠道（Google Play、社交媒体等）的数据采集。
- 不做应用内埋点 / 行为数据分析（仅以评论为数据源）。
- 不生成可直接上线的生产代码或 UI 设计稿（产出为 PRD 与测试用例文档）。
- 不承诺实时无限量抓取；数据获取受来源方速率限制与条款约束。

## 2. 用户与使用场景

### 2.1 目标用户

| 角色 | 描述 | 主要诉求 |
| --- | --- | --- |
| 产品经理 | 将用户反馈转化为迭代计划 | 快速获得有证据支撑的发现、PRD 与版本规划 |
| 数据分析师 | 清洗、分类、统计评论 | 获得干净结构化数据与分类结果 |
| 测试工程师 | 基于需求编写测试 | 获得可追溯到评论的测试用例 |
| 面试官 / 评审者 | 评估候选者能力 | 验证通用性、可追溯性、模型驱动能力与本地可运行性 |

### 2.2 核心使用场景

1. **主流程**：输入美国区 App Store 链接 → 选择模型提供商并填写 Key → 点击"开始" → 10 阶段工作流自动执行 → UI 展示进度与交付物。
2. **目标约束**：附加分析目标/约束（如"聚焦订阅转化"、"关注可用性"、"只看某版本"、"只看低分评论"），系统据此动态确定分析范围。
3. **数据导入**：无法联网或需复现时，导入符合文档规范的 JSON / CSV 评论数据，直接进入清洗及后续流程。
4. **离线评审**：评审者在无外网 / 无 Key 环境下，通过仓库内**明确标注的缓存数据**查看样例输出。
5. **模型自选**：用户可自由切换提供商（OpenAI / Anthropic / DeepSeek / Gemini / Ollama 本地 / 自定义），满足不同评审环境。

### 2.3 用户故事

- 作为产品经理，我希望系统根据我指定的分析目标动态确定范围，以便结果聚焦于我关心的问题。
- 作为产品经理，我希望每条发现都附有来源评论、样本数、置信度与冲突证据，以便判断可信度。
- 作为测试工程师，我希望每个测试用例都能追溯到需求与原始评论，以便验证"需求是否解决了用户提出的问题"。
- 作为评审者，我希望系统能处理未见过的链接、混合语言、重复/矛盾评论、证据不足等场景，且**不伪造数据**。
- 作为使用者，我希望选择任意主流 LLM 提供商并填写自己的 Key，而不是被锁定在某一家。

## 3. 功能需求（Functional Requirements）

### 3.0 总体工作流（10 阶段）

系统在用户点击"开始"后依次执行，UI 实时呈现阶段状态、中间结果、验证结果、错误与修订记录：

```mermaid
flowchart LR
    A[1. 确定分析范围] --> B[2. 采集评论数据]
    B --> C[3. 清洗·去重·结构化]
    C --> D[4. 动态分类与分析]
    D --> E[5. 证据充分性评估]
    E --> F[6. 更新计划与 PRD]
    F --> G[7. 生成测试用例]
    G --> H[8. 可追溯性验证]
    H --> I[9. UI 展示执行进度]
    I --> J[10. 展示中间与最终交付物]
```

### 3.1 输入模块（FR-1）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1.1 | 支持输入**美国区（us）** App Store 应用链接，解析出应用 ID 与名称 | P0 |
| FR-1.2 | 支持输入**分析目标/约束**（自由文本），如订阅转化、可用性、指定版本、仅低分评论；支持多个约束组合 | P0 |
| FR-1.3 | 链接校验：非法链接、非美国区、非 App Store 链接给出明确错误提示 | P1 |
| FR-1.4 | 支持"开始"按钮触发完整工作流；运行期间可查看各阶段状态与进度 | P0 |
| FR-1.5 | 支持从本地导入 JSON / CSV 评论数据（格式见 FR-9），导入数据直接进入清洗及后续阶段 | P0 |
| FR-1.6 | **模型选择**：内置常见 LLM 提供商列表（OpenAI / Anthropic / DeepSeek / Gemini / 本地 Ollama / 自定义），选择后自动带出默认 `base_url` 与候选模型 | P0 |
| FR-1.7 | 用户填写 API Key；本地模型（Ollama）允许留空 | P0 |
| FR-1.8 | 提供"测试连接"功能，在开始前验证所选模型配置可用 | P1 |

### 3.2 数据采集模块（FR-2）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-2.1 | 通过 **Apple 官方 RSS Review Feed** 与 **iTunes Lookup API** 采集（优于抓取页面可见内容），并在文档中说明采集方式、数据源与局限 | P0 |
| FR-2.2 | 采集字段至少包含：评论 ID、标题、正文、评分（1–5 星）、版本、更新时间、作者；来源不可得则明确标注缺失 | P0 |
| FR-2.3 | 遵守速率限制：串行请求、间隔节流、429/5xx 指数退避；不产生异常负载 | P0 |
| FR-2.4 | 采集失败（网络、限流、超时、无数据）给出结构化错误；部分失败如实记录，不中断整体流程 | P0 |
| FR-2.5 | 原始数据落盘缓存（标注来源与采集时间），用于离线评审与可复现性 | P1 |

### 3.3 数据清洗与结构化模块（FR-3）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-3.1 | 字段标准化：评分归一整数、日期归一标准格式、去除 HTML 实体/控制字符/多余空白 | P0 |
| FR-3.2 | 去重：**精确去重**（规范化后 hash）+ **近似去重**（归一化后分片 Jaccard 相似度 ≥ 0.85），保留代表条并记录 `dup_group` | P0 |
| FR-3.3 | 语言识别与标记（支持混合语言），为语义分析提供输入 | P1 |
| FR-3.4 | 派生字段：评分分桶（1–2 星为低分）、版本号规范化、评论长度等统计特征 | P1 |
| FR-3.5 | 清洗采用**确定性规则**，产出清洗报告（去重数量、字段缺失统计），并在文档说明选型理由 | P1 |

### 3.4 动态分类与分析模块（FR-4，模型驱动核心）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-4.1 | **动态主题发现**：模型从实际评论中归纳主题，不使用固定关键词映射或预定义分类体系；不同应用/不同目标下主题应不同 | P0 |
| FR-4.2 | **问题整合**：将分散评论聚合成可操作的用户问题，附带证据链 | P0 |
| FR-4.3 | **基于证据的分析**：每个发现必须包含——来源评论 ID/摘录、支持样本数、置信度、不确定性、冲突证据；**模型结论与确定性统计必须可区分**（`kind: model_derived / deterministic_stat`） | P0 |
| FR-4.4 | 批次化处理超出 token 预算的评论，批次结果由确定性逻辑汇总 + 模型二次整合 | P1 |
| FR-4.5 | 代码对模型产出的 `supporting_count` 与 `evidence_review_ids` 做**确定性复核**，不一致则修订为统计值并记录修订 | P0 |
| FR-4.6 | 支持按用户约束过滤/聚焦分析（如仅低分、仅某版本） | P0 |

### 3.5 证据充分性评估模块（FR-5）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-5.1 | 评估每类结论的证据量（样本数、版本/时间覆盖度），不足时明确标注"证据不足/不确定性" | P0 |
| FR-5.2 | 识别**矛盾反馈**（同一问题正反意见并存），单独呈现冲突证据 | P0 |
| FR-5.3 | 如实报告数据局限：样本量小、仅部分版本、采集受限、语言分布偏斜等；**不得伪造数据** | P0 |

### 3.6 PRD 生成模块（FR-6）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-6.1 | 基于用户问题与发现生成 PRD：需求 ID、标题、描述、优先级（P0/P1/P2）、边界 | P0 |
| FR-6.2 | 制定更新计划，必要时将范围**拆分为多个版本**（如 V1/V2）并说明拆分理由 | P0 |
| FR-6.3 | 每条需求必须引用 ≥1 个 finding 与 ≥1 条真实评论；无法支撑的标记为假设 | P0 |

### 3.7 测试用例生成模块（FR-7）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-7.1 | 依据 PRD 生成测试用例，每个用例**关联其需求**与**来源用户评论** | P0 |
| FR-7.2 | 用例应能验证"对应需求是否解决了评论中提出的问题" | P0 |
| FR-7.3 | 用例字段：ID、关联需求 ID、关联评论 ID、前置条件、步骤、预期结果 | P1 |

### 3.8 可追溯性验证模块（FR-8）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-8.1 | 校验完整链路：**评论 → 发现 → 需求 → 测试用例**（所有引用的 ID 必须真实存在；孤立发现/孤立需求/孤儿用例列入报告） | P0 |
| FR-8.2 | 对无证据支撑的结论执行三选一：**删除 / 修订 / 明确标注为假设** | P0 |
| FR-8.3 | 输出验证报告：通过项 / 修订项 / 删除项 / 假设项及原因 | P1 |

### 3.9 数据导入格式规范（FR-9）

- **JSON**：数组或对象，每条评论含必填字段 `id`、`title`、`content`、`rating`（1–5）；可选 `version`、`lang`、`country`、`date`、`author`。
- **CSV**：表头 `id,title,content,rating,version,lang,country,date,author`，UTF-8 编码。
- 导入时校验必填字段，缺失/非法值给出明确提示；导入数据同样进入清洗及后续全流程。

### 3.10 运行管理与历史（FR-10）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-10.1 | 每次运行生成唯一 `run_id`，元数据（应用、目标、模型、状态、时间、缓存标注）入库 | P0 |
| FR-10.2 | 支持历史运行列表查看与重新打开 | P1 |
| FR-10.3 | 缓存数据在 UI 中以醒目标识（如"⚠ 缓存演示数据"）标注，且**不替代**联网+有 Key 时处理新输入的能力 | P0 |

### 3.11 UI 展示模块（FR-11）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-11.1 | 工作流进度面板：10 阶段实时状态（待执行/执行中/完成/失败/降级/已修订）、耗时、错误信息 | P0 |
| FR-11.2 | 交付物展示：原始评论、清洗数据、主题分类、发现、证据报告、PRD、测试用例、追溯报告，均可查看/下载 | P0 |
| FR-11.3 | 发现面板区分展示 **📊 确定性统计** 与 **🤖 模型结论**，卡片可展开证据评论原文 | P0 |
| FR-11.4 | 追溯报告以评论→发现→需求→用例链路呈现（树状/图） | P1 |
| FR-11.5 | 失败阶段显示错误并支持"重试本阶段" | P1 |
| FR-11.6 | 前端基于 **Vue 3 + Vite** 构建，由后端静态托管，一条命令启动全栈 | P0 |
| FR-11.7 | 响应式布局；界面语言支持中英文 | P1 |

## 4. AI 需求（模型驱动要求）

### 4.1 模型驱动语义任务（必须满足）

以下核心语义任务**至少一项**由模型（LLM）驱动且为运行期动态执行：

- 动态主题发现（FR-4.1）
- 问题整合（FR-4.2）
- 基于证据的分析（FR-4.3）
- 需求生成（FR-6）
- 测试用例生成（FR-7）

> 约束：仅通过固定关键词、正则、查找表或手动预定义映射实现全部语义分析 → 不满足要求。模型驱动的语义能力必须泛化到**未见过的评论、应用与分析目标**。

### 4.2 各环节技术选型原则（须在文档中说明"为何这样选"）

| 环节 | 方式 | 理由 |
| --- | --- | --- |
| 数据采集、去重、字段标准化、校验、追溯验证 | **确定性规则** | 可复现、可审计、无幻觉风险 |
| 主题发现、问题整合、发现生成、需求/用例生成 | **语言模型** | 语义理解、跨语言、泛化到未见输入 |
| 统计指标（样本数、评分/版本分布） | **统计方法** | 精确、可复现 |
| 近似去重相似度、语言识别 | 规则 + 统计/轻量检测 | 可解释、可离线 |

### 4.3 模型配置与工程要求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| AI-1 | 文档记录：各提供商与模型、主要提示词/工具定义、模型配置（温度、max tokens） | P0 |
| AI-2 | 定义**故障处理策略**：超时、限流、无效输出（JSON 解析失败）的退避重试与降级 | P0 |
| AI-3 | 制定**降低幻觉/无依据结论**措施：提示词强制"只引用真实 review_id、禁止编造、无证据标注 assumption、统计与确定性结果一致"；低温度（分析 0.2 / 写作 0.4）；结构化输出 | P0 |
| AI-4 | 全部语义输出采用 JSON Schema 结构化，客户端校验，失败重试 1 次后降级 | P1 |
| AI-5 | 模型结论与确定性统计在输出中**明确区分**（字段 + UI 分区） | P0 |
| AI-6 | 模型阶段失败时降级为"证据不足/需模型阶段"说明，结果透明标注，不伪造 | P0 |

### 4.4 多提供商与密钥安全

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| AI-7 | 内置 Provider Registry（JSON 配置）：OpenAI / Anthropic / DeepSeek / Gemini / 本地 Ollama / 自定义；新增厂商不改代码 | P0 |
| AI-8 | 统一 OpenAI 兼容协议；本地 Ollama 无需 Key | P0 |
| AI-9 | 用户 Key 仅经请求头传入后端**内存**上下文使用；**禁止**写入 `.env`、日志、缓存、数据库、中间产物 | P0 |
| AI-10 | 后端支持环境变量默认配置（`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`），UI 输入优先；提供 `.env.example`，不含真实密钥；`.gitignore` 排除 `.env` | P0 |

## 7. 交付物要求

1. **GitHub 项目链接**，包含：
   - 完整源代码；
   - 依赖配置（`requirements.txt` / `package.json`）；
   - 运行说明（安装、配置、构建、启动）；
   - 数据采集方法说明（数据源与局限）；
   - **明确标注的样例输出/缓存数据**（供无外网评审）；缓存不得替代联网处理新输入的能力；
   - **完整 commit 历史**，展示实现、迭代与 vibe coding 过程。
2. 支持从 JSON / CSV 导入评论（格式文档化，见 FR-9）。
3. 不接受"不可运行的纯文档提交"。

## 9. 边界与异常场景处理

| 场景 | 预期行为 |
| --- | --- |
| 非法/非美国区链接 | 明确错误提示，不启动工作流 |
| 评论数据量极少（如 < 20） | 如实报告证据不足，标注不确定性，不伪造数据 |
| 混合语言评论 | 语言标记 + 模型跨语言分析 |
| 重复 / 近似重复评论 | 规则去重并记录 `dup_group` |
| 矛盾反馈 | 单独呈现冲突证据 |
| 采集失败 / 限流 | 结构化错误、退避重试、部分成功如实记录、可重试 |
| 模型无 Key / 连接失败 | 阶段降级为"需模型/证据不足"说明，透明标注 |
| 模型输出非法 JSON | 重试 1 次 → 降级并记录 |
| 无外网 / 无 Key 评审 | 使用标注的缓存数据演示，UI 明确标识"缓存" |

## 10. 验收标准（Acceptance Criteria）

1. 本地按 README 步骤可成功运行（含前端构建），输入示例链接 + 选择任一内置模型 + 填 Key 后点击"开始"，10 阶段工作流完整执行并在 UI 展示进度与交付物。
2. 在指定目标（如"聚焦订阅转化"）下，输出主题/发现与默认目标不同，证明非硬编码。
3. 导入一份全新 JSON/CSV 评论数据（非示例应用），系统仍产出有依据的发现、PRD 与测试用例。
4. 每条发现均含：来源评论 ID/摘录、样本数、置信度、冲突证据；模型结论与统计结论可区分。
5. 可追溯性验证报告显示评论→发现→需求→测试用例链路完整；无依据结论被删除/修订/标注假设。
6. 测试用例覆盖 PRD 需求且关联具体评论。
7. 至少两种内置模型提供商可用（含一种本地/无需 Key 的选项）；Key 不落盘；仓库不含真实密钥，含 `.env.example`。
8. 缓存数据明确标注且可离线查看；commit 历史完整；采集方式有文档说明并符合速率限制。
